# `PublisherOp`: Holoscan to DDS

`rti::holoscan::dds::PublisherOp<DdsType, Adapter>` is a reusable Holoscan
operator that publishes graph data through RTI Connext DDS.

```text
upstream Holoscan operator
          |
          | Adapter::holoscan_type
          v
       PublisherOp -- Adapter::to_dds() --> DataWriter<DdsType> --> DDS
          |
          | unchanged original payload
          v
 optional downstream Holoscan operator
```

## Template arguments

### `DdsType`

The C++ type generated by RTI Code Generator from application IDL. For
example:

```cpp
#include "Telemetry.hpp"

using DdsType = rti::holoscan::example::Telemetry;
```

The generated type is used to create the typed DDS topic and
`dds::pub::DataWriter<DdsType>`.

### `Adapter`

The adapter selects the Holoscan input type and converts it to `DdsType`:

```cpp
struct TelemetryAdapter {
  using holoscan_type = std::uint32_t;

  static Telemetry to_dds(holoscan_type index) {
    Telemetry sample;
    sample.sensor_id = 7;
    sample.sample_index = index;
    sample.value = 1000.0 + index * 0.5;
    return sample;
  }
};
```

The required contract is:

```cpp
using holoscan_type = /* valid Holoscan graph payload */;
static DdsType to_dds(const holoscan_type& value);
```

A by-value parameter is also valid when the declared function can be called
with a const reference, as in the scalar example above.

If `holoscan_type` is `holoscan::Tensor`, the adapter must also provide:

```cpp
static holoscan::TensorInputSpec tensor_input_spec();
static holoscan::TensorOutputSpec tensor_output_spec();
```

Those methods declare dtype, rank, memory kind, bounds, storage, and transfer
behavior to the Holoscan graph compiler. See
[`ShapeXcdrAdapter`](../../applications/shapes_demo_xcdr/shape_xcdr.hpp).

## Constructor

```cpp
explicit PublisherOp(const EndpointConfig& config);
```

The configuration is copied into the operator. The minimum usable
configuration supplies `topic_name`:

```cpp
const rti::holoscan::dds::EndpointConfig config{
    .topic_name = "RobotState",
};
```

See [endpoint configuration](configuration.md) for every field and default.

## Ports

| Port | Direction | Type | Meaning |
|---|---|---|---|
| `input` | Input | `Adapter::holoscan_type` | Payload converted and written to DDS |
| `published` | Output | `Adapter::holoscan_type` | The same payload after a successful `DataWriter::write()` call |

The `published` port is useful for local progress tracking or for continuing
the graph after publication. It does not mean that a remote reader has
received or acknowledged the sample.

## Activation and lifecycle

- The contract uses `OnEach{input}`: one queued input activates `compute()`.
- `start()` loads the XML QoS and creates the participant, publisher, topic,
  and writer.
- `start()` waits up to `reader_match_timeout` (ten seconds by default) for at
  least one compatible reader when `wait_for_reader` is enabled. Set it to
  `false` for a publisher that may start before its readers.
- `compute()` receives one graph payload, calls `Adapter::to_dds()`, writes the
  DDS sample, and emits the original payload on `published`.
- `stop()` waits up to five seconds for acknowledgements when applicable, then
  releases DDS entities in dependency order.

The reader-match policy and all lifecycle wait intervals are configurable in
`EndpointConfig`.

## Adding it to a graph

```cpp
using RobotPublisher =
    rti::holoscan::dds::PublisherOp<RobotState, RobotStateAdapter>;

holoscan::Graph graph{"robot-publisher"};
const auto source = graph.op<RobotSource>("robot-source");
const auto publisher = graph.op<RobotPublisher>(
    "robot-dds-publisher",
    rti::holoscan::dds::EndpointConfig{
        .domain_id = 0,
        .topic_name = "RobotState",
        .qos_file = "RobotQos.xml",
        .qos_profile = "RobotLibrary::RobotProfile",
    });

graph.add_flow(source->output, publisher->input);
graph.partition("robot-publisher-partition").add(source).add(publisher);
```

The graph must run with a working directory from which `qos_file` can be
opened. The examples copy their XML file into the matching build directory.

## Common failures

- **Empty topic:** `start()` throws `DDS topic name must not be empty`.
- **Missing QoS file/profile:** Connext reports an XML/QoS lookup error.
- **No compatible reader:** startup times out after the configured deadline.
- **Type mismatch:** DDS discovery does not match the writer and reader.
- **Tensor contract mismatch:** Holoscan rejects the graph during compile.
- **License failure:** Connext cannot create DDS entities.
