# `SubscriberOp`: DDS to Holoscan

`rti::holoscan::dds::SubscriberOp<DdsType, Adapter>` is a reusable Holoscan
source operator that receives RTI Connext DDS samples and emits graph payloads.

```text
DDS --> DataReader<DdsType> --> Adapter::from_dds() --> SubscriberOp
                                                            |
                                                            | Adapter::holoscan_type
                                                            v
                                               downstream Holoscan operator
```

## Template arguments

### `DdsType`

The C++ type generated by RTI Code Generator. It determines the typed DDS
topic and `dds::sub::DataReader<DdsType>`.

### `Adapter`

The adapter selects the Holoscan output type and converts a DDS sample:

```cpp
struct TelemetryAdapter {
  using holoscan_type = std::uint32_t;

  static holoscan_type from_dds(const Telemetry& sample) {
    return sample.sample_index;
  }
};
```

The required contract is:

```cpp
using holoscan_type = /* valid Holoscan graph payload */;
static holoscan_type from_dds(const DdsType& sample);
```

If `holoscan_type` is `holoscan::Tensor`, the adapter must additionally
provide `tensor_output_spec()`. The XCDR example also supplies
`tensor_input_spec()` because its application decodes that output later.

## Constructor

```cpp
explicit SubscriberOp(const EndpointConfig& config);
```

Publisher and subscriber must use compatible domain IDs, topic names, DDS
types, and QoS. See [endpoint configuration](configuration.md).

## Port

| Port | Direction | Type | Meaning |
|---|---|---|---|
| `output` | Output | `Adapter::holoscan_type` | One converted payload for each valid DDS sample |

The current output declaration admits a burst of at most 32 emissions per
activation. The example QoS and graph queues are sized consistently with that
prototype limit.

## Event-driven activation

The subscriber does not poll DDS from every Holoscan scheduler cycle:

1. `start()` creates the participant, subscriber, topic, and reader.
2. A dedicated thread waits on a Connext `WaitSet` containing the reader's
   `DATA_AVAILABLE` status condition and a shutdown guard condition.
3. When data becomes available, the thread posts a bounded Holoscan
   `NotificationSource`.
4. `OnNotified` activates `compute()` on the Holoscan scheduler.
5. `compute()` takes valid samples, calls `Adapter::from_dds()` for each one,
   and emits the resulting graph payloads.
6. The waiter is rearmed after the activation drains the available samples.

The waiting thread never executes graph work and does not block a Holoscan
execution lane.

## Lifecycle

- The notification sender is acquired during the Holoscan `kArm` lifecycle
  stage.
- DDS entities and the wait thread are created in `start()`.
- `stop()` triggers the guard condition, joins the thread, detaches conditions,
  and releases DDS entities.
- A wait-thread failure is reported through the next Holoscan activation.

## Adding it to a graph

```cpp
using RobotSubscriber =
    rti::holoscan::dds::SubscriberOp<RobotState, RobotStateAdapter>;

holoscan::Graph graph{"robot-subscriber"};
const auto subscriber = graph.op<RobotSubscriber>(
    "robot-dds-subscriber",
    rti::holoscan::dds::EndpointConfig{
        .domain_id = 0,
        .topic_name = "RobotState",
        .qos_file = "RobotQos.xml",
        .qos_profile = "RobotLibrary::RobotProfile",
    });
const auto sink = graph.op<RobotSink>("robot-sink");

graph.add_flow(subscriber->output, sink->input);
graph.partition("robot-subscriber-partition").add(subscriber).add(sink);
```

Start this application before the matching publisher when using the supplied
examples.

## Common failures

- **No data arrives:** check domain, topic, type, QoS compatibility, and
  network discovery.
- **The graph does not compile:** the adapter output is not an admitted
  Holoscan payload or its Tensor contract disagrees with the consumer.
- **Conversion fails:** `Adapter::from_dds()` rejected or could not decode the
  sample. The XCDR example reports malformed or oversized buffers this way.
- **Shutdown hangs:** treat it as a bug; the guard condition is intended to
  wake and join the DDS wait thread deterministically.
